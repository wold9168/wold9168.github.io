遇到一个很牛逼的 DNS 开销问题。

某测试用 K8s 集群内，curl 测试时，DNS 延迟飞到了 20ms，也不清楚是什么原因：

以下的 `test-shell` 是以以下指令创设的一台设备：

```bash
kubectl --context kind-cross-test-1 run test-shell --image=debian:12 --rm -it \                                   ─╯
--restart=Never \
--image-pull-policy=Never \
-- \
  bash
```

# 问题表征

```bash
root@test-shell:/# curl -x socks5://tailscale-proxy.default.svc.cluster.local:1055 -k -s -w "DNS: %{time_namelookup}s
TCP: %{time_connect}s

TTFB: %{time_starttransfer}s
Total: %{time_total}s
```

# 问题解决

折腾了几天，随求助于 D 指导，用`strace`手忙脚乱分析一通，D 指导忽然发散思维，指出 `/etc/resolv.conf` 可能存在问题。

遂翻阅 `resolv.conf` 送呈 D 指导：
```bash
root@test-shell:/# cat /etc/resolv.conf
search default.svc.cluster.local svc.cluster.local cluster.local openstacklocal
nameserver 10.96.0.10
options ndots:5
```

D 指导的原话是：

> 实际发生的查询顺序是：
> 
> - 先查 tailscale-proxy.default.svc.cluster.local.**default.svc.cluster.local**（拼接第一个 search 域）—— 失败（NXDOMAIN）
> - 再查 tailscale-proxy.default.svc.cluster.local.**svc.cluster.local** —— 失败
> - 再查 tailscale-proxy.default.svc.cluster.local.**cluster.local** —— 失败
> - 再查 tailscale-proxy.default.svc.cluster.local.**openstacklocal** —— 失败
> - 最后才查 tailscale-proxy.default.svc.cluster.local.（不加任何后缀的原始域名）—— 成功！
> 
> 虽然 DNS 服务器对每次失败查询都很快（约 1ms），但连续进行 4~5 轮查询的累积耗时（网络往返 + 客户端处理），就构成了您看到的 20~25ms。
